## Run a Bot 功能概览

| 功能 | 首版范围 |
| --- | --- |
| 连接 BrowserAct | 使用已配置的 API Key |
| 选择运行来源 | 在 BrowserAct 插件下选择“运行我的 Bot”或“运行官方模板”工具，不再设置独立来源参数 |
| 选择运行目标 | 展示对应来源的 Bot 或模板供选择 |
| 选择操作模式 | 两个工具新建节点默认“查看参数”，用户手动切换“运行 Bot”；不按模式额外拆分工具 |
| 查看参数 | 读取所选目标的输入定义，只返回可复制修改的参数值对象，不附带说明或 Schema，不启动任务 |
| 填写运行参数 | 通用参数独立填写，Bot 业务输入使用 JSON；用户提供的字段覆盖 Bot 默认值；官方模板支持代理地区选择 |
| 启动并等待 | 启动任务后由插件内部轮询，用户在同一个节点内等待结果 |
| 返回结果 | 对齐自家 n8n/Zapier，返回 API 任务详情 JSON，保留字段及文件链接，首版不转存为 Dify `files`；异常情况明确反馈 |

首次配置流程：配置连接 → 选择“运行我的 Bot”或“运行官方模板”工具 → 从该工具的下拉列表选择目标 → 选择“查看参数”并单步运行 → 点击“复制全部输出” → 整体粘贴到自定义参数 JSON → 修改其中 `json[0]` 的参数配置 → 切回“运行 Bot” → 执行节点并等待结果。已了解参数的用户可直接使用“运行 Bot”。

## 已确认

### Bot 来源

首版同时支持“我的已发布 Bot”和“官方模板”。

### Bot 选择方式

用户已确认首版采用两个按来源区分的工具和“下拉选择 Bot + JSON 输入业务参数”：运行我的 Bot 只加载账号下已发布 Bot，运行官方模板只加载官方模板，均展示名称、使用对应 ID。来源由工具身份确定，不依赖节点参数联动；不再采用合并来源列表的候选。关键词搜索暂不作为首版要求，控件效果仍需联调。输入清单与证据见 [输入参数与选择方式](03-run-inputs.md)。

### 参数输入方式

采用通用参数独立填写、业务参数使用 JSON 的方式：

- 通用参数使用独立字段。具体开放哪些通用参数、名称和默认值，后续逐项确认。
- 我的已发布 Bot 和官方模板均通过一个业务输入字段接收 JSON 对象；用户可以直接填写，也可引用上游生成的 JSON 字符串。
- 插件运行前从完整 Dify 输出中提取 `json[0]`，忽略外层 `text`、`files`；保留纯参数对象和 `{}` 输入。读取所选 Bot 或模板的 `input_schema` 中明确提供的默认值；双方同一路径均为对象时逐层合并，数组整体替换，其他显式用户值优先，校验后构造运行请求的 `input` 对象。
- 未提供的字段保留已定义的默认值；必填字段既无默认值也未提供时，提示补充。`0`、`false` 等是有效输入，不能当作未提供。显式空值仍需符合对应字段的 Schema。
- 不需要覆盖参数时提供 `{}`；这表示不覆盖默认值，不保证缺少必填值的 Bot 也能运行。
- 首版不要求选择 Bot 后动态生成独立业务输入控件。可复制 JSON 通过同一节点的“查看参数”模式提供，不再输出参数说明；嵌套对象逐层合并、数组整体替换已确认，避免只改部分字段时丢失其余默认字段。

决定来源：在核对 Dify 动态字段限制并比较替代方案后，用户最新明确确认“就使用json输入的方案吧”，接受前述“JSON 输入覆盖 Bot 默认值”的方向。该决定替代此前参考 Make 的逐字段动态表单要求。

默认值合并由插件明确实现，不假定 BrowserAct API 自动补齐；公开契约要求最终 `input` 符合 Schema，但没有明确保证服务端默认值填充。Dify 动态字段限制见 [参数调研](../research/02-bot-input-parameters.md)，Make 界面记录保留作历史交互参考。

### 运行操作划分

这里的“指令”指 Dify 中用户可添加的工具操作，不要求与每一个 API 接口一一对应。

2026-10-19 用户最新确认：一个 BrowserAct 插件提供“运行我的 Bot”和“运行官方模板”两个工具，分别声明输入与列表加载接口；两个工具都保留“查看参数”和“运行 Bot”两种模式及 JSON 业务输入，新建节点均默认“查看参数”，不自动切换为运行。该决定替代此前单个 `Run a Bot` 加来源参数的方案，不新增独立任务查询工具。Provider 凭据与内部 API、输入转换、轮询和输出逻辑可共享，不复制成两个插件。

### 查看参数模式与输出

2026-10-19 用户已确认以下行为：

- 用户选择目标和“查看参数”模式后，点击 Dify 已有的节点单步运行入口；选择 Bot 本身不触发自动展示、字段回填或模式切换。
- 插件只读取对应 Bot/模板的详情，从 `input_schema` 提取参数值对象；不启动任务，不轮询任务状态，也不返回任务执行结果或 `task_id`。
- 查看模式只返回可直接作为自定义参数 JSON 的对象：在 Dify 的 `json[0]` 中放实际输入字段和值，不再增加说明、类型、约束、Bot 信息、提示清单或 `default_inputs` 包装。正常 `text` 为空、`files` 为空数组。
- 只提取 Schema 明确提供的默认值，保留字段名大小写和原始 JSON 类型；`0`、`false`、空字符串等不能因值为假而被丢弃。无默认值的字段不虚构占位值，运行时仍按 Schema 校验并提示补充缺失必填项。
- 用户点击原生“复制全部输出”，整体粘贴到自定义参数 JSON，修改 `json[0]` 中的参数，例如 `search_input`。插件提取该对象，不把外层包装、Schema 或整个 Bot 详情作为业务参数。
- 插件通过标准 JSON 消息返回参数值对象；按已核查的 Dify 1.17.1，节点“上次运行”仍以一个只读 JSON 编辑器展示整个 `text/json/files`。移除的是插件可控制的业务字段，不承诺删除 Dify 自带外层包装或自定义结果界面。
- 原生复制按钮复制整个编辑器输出，用户直接粘贴全部内容即可，无需手动提取对象。运行前由插件提取 `json[0]`，忽略外层 `text`、`files`；不增加专用复制按钮。完整输出的识别和错误规则见 [评审稿输入约定](04-review-design.md#业务-json-与默认值)。
- 查看模式不使用自定义业务 JSON、代理地区或任务等待时限，不因这些运行参数未填写或业务 JSON 不合法而阻止查看；不依赖 Dify 条件隐藏字段。
- 模式相关要求在执行时校验，失败通过 Dify 原生节点错误反馈；不承诺插件在编辑参数时实时校验 JSON、标红兄弟字段或动态修改帮助与必填标记。
- 若输入定义未提供，返回明确的节点错误，不把它伪装成空配置；Schema 有效但没有可提取默认值时返回 `{}`，这不表示无默认值的必填参数已满足。查看成功不保证仅用默认配置即可运行。
- 查看成功仅表示已读取参数定义，不表示 Bot 执行成功。用户修改参数后需手动切回“运行 Bot”，再进行正式工作流测试或发布。

执行后也不自动回填：点击“运行此步骤”取得 `json[0]` 参数对象后，插件不能通过标准接口将结果写入同一节点 `tool_parameters`。`create_variable_message()` 创建的是输出变量，不是修改同名输入框。首版保留手动复制/粘贴，或直接输入 `{}` 使用默认值；需要改动时只填写覆盖字段即可。下游引用属于运行时取值，不等于回写本节点配置。证据见 [执行后回填边界](../research/02-bot-input-parameters.md#执行完成后能否回填当前节点的-json-配置)。

输入数据能力已通过两个 Bot、六个模板的真实只读接口验证，见 [API 实测](../research/evidence/2026-10-19-bot-api/README.md)。原生编辑器的固定版本证据见 [输出界面边界](../research/02-bot-input-parameters.md#原生结果编辑器与插件输出的边界)。本节确认的是数据与操作流程，目标 Dify Cloud 的实际显示、复制体验仍需联调；原型已移除自定义参数展示组件，不将原型或 API 验证当作界面已实现。

### 运行返回方式

“运行 Bot”模式只做同步等待结果返回。该决定替代此前“等待/仅提交”双模式及其配套工具方案，适用于我的已发布 Bot 和官方模板；“查看参数”不创建任务，不属于仅提交模式。

- 只保留同步等待模式，移除“等待完成”开关和仅提交模式。
- 用户执行 `Run a Bot`，插件启动 BrowserAct 任务、内部轮询状态、获取结果，随后结束当前工具节点；串行下游节点再使用结果。
- 内部轮询模式已由用户明确确认，属于首版执行方式；具体轮询参数不在本阶段继续细化。
- BrowserAct 启动 API 本身仍返回 `task_id`；同步等待由插件适配层实现，不要求服务端新增同步 API。
- 竞品证据与建议调用链见 [03：任务等待机制](../research/03-task-waiting.md)：Firecrawl Crawl 在插件内轮询，Apify 将等待封装在 SDK 内；具体间隔和超时不能直接照搬。
- `task_id` 仍用于内部查询、排错，也可作为返回元数据；不将仅返回任务 ID 视为正常完成。
- 查询到 `pausing/paused` 时立即停止轮询并结束等待，节点以失败报告当前状态并保留 `task_id`，不自动恢复或取消远端任务；节点失败不等于远端任务状态为 `failed`。此项已确认。
- 失败、取消或超时不伪装成已成功取得结果；超时遵循 R2，其他具体输出/错误语义仍待确认。

### 任务管理范围

首版按同步运行范围收敛，不单独开放 `Get Task`、`Get Task Status`、`Cancel Task`、`Resume Task`，也不设计回调触发流程。此前为仅提交模式确认的 `Get Task` 不再作为当前首版工具；尚未回答的独立取消工具问题不再继续推进。

轻量状态查询、读取任务详情等 API 是 `Run a Bot` 内部能力。R2 已确认：达到用户设置的等待超时后，只结束节点等待并报告超时，保留 `task_id`；不调用取消接口，远端任务按自身状态继续执行。
